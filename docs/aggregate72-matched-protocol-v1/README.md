# Registered aggregate72 matched-VM disk protocol

Protocol SHA-256: `394b422c61409e27547ea471293e4406d9d8513f4bee6751762e4dc5d6e937cf`. This protocol and its runtime source hashes were fixed before any scored requests under this timing design. Earlier qualification outputs and preparation observations were inspected; the curated cohort is not blind.

Four engines run serially on their owned disk-backed stores in the same existing 16.8 GB, ten-vCPU Linux VM. Each container receives a four-CPU quota and 12 GiB memory with no extra swap; CPU affinity is not pinned. All images are pinned arm64 images. rdfdb is source 9a2f49b, freshly built from verified container-local source, with ELF SHA-256 4194d984202d1ee20d57e0a51f4a29928a908a55963808dbd50c5ccbb6c33a68. Image, module, binary, validator, reference and store identities are in protocol.json.

Pass 1 uses rdfdb, DuckDB, Virtuoso, QLever on LUBM then WatDiv. Pass 2 reverses the engine order and dataset order. Each fresh engine phase runs its complete dataset workload once as warmup, then once as measurement. Across both passes there are 16 phases, 576 excluded warmup requests and 576 scored requests. The 72 labels contain 68 distinct exact query texts: 26 LUBM texts under 30 labels and 42 WatDiv texts. Both labeled totals and a predefined unique-hash view will be reported; the latter sums the within-phase mean latency of each duplicate-hash group. Query-label order remains fixed in both passes.

Eligibility requires every warmup and measured output to pass the unchanged, separately preregistered COUNT-compatible gate, with primary exact-term outcomes reported separately. QLever's earlier primary outcome is 0/72 while its COUNT-compatible outcome is 72/72. No incomplete or unqualified engine/dataset gets a comparative total. Failures stop the attempt and remain preserved; no sample deletion or automatic retry. Both order-pass totals and per-query observations remain visible; no pooled significance or general SOTA claim follows from two passes.

Latency runs from HTTP submission to complete body receipt. SQL translation, planning, execution, fetch, serialization and transport are included inside each HTTP request; validation, cache-control calls and log writes are outside the clock. The SQL baseline is the frozen lossless typed triples table and scoped translation, with no added property tables or numeric indexes. The Docker HTTP adapter passed COUNT and complete grouped-output preflights against fixed references. This is an end-to-end HTTP comparison of these configurations, not engine-only or embedded API latency.

All phases use fresh processes and a complete workload warmup. OS pages are not cleared; this is a shared host. QLever's result cache is verified clear before every warmup and measured request. Other engine caches use their stated defaults; the harness has no external result cache. HTTP requests set Cache-Control:no-cache and Accept-Encoding:identity. rdfdb waits for statistics. Virtuoso's owned store permits administrative writes on reopen/checkpoint, so it is validated by source provenance, full graph counts and all query results, rather than claiming byte-immutable database files. rdfdb, SQL and QLever store hashes are checked before and after each phase.

Memory is container cgroup memory.peak, including startup, warmup, measured queries, probes and charged file/kernel pages; it is not process RSS or per-query execution-only memory. The host already has swap usage; before/after host observations and both orders will be retained. Scratch guards remain active throughout, with sampling limitations. Existing qualification evidence is linked in the other aggregate72 reports. The measurement attempt has not started at this registration snapshot.

No credentials, private keys or database blobs are included. SHA256SUMS.json hashes every file except itself. Historical absolute paths identify the intended environment and require explicit adaptation before replay.
