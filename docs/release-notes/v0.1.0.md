# TripleLight 0.1.0 release notes

Status: draft for review. This is the first release. The packages are prepared (crates.io metadata, PyPI wheels, npm
tarballs; see "Packages" below) and have not been uploaded at the time of writing.

TripleLight is an embedded RDF database for analytical SPARQL 1.1 queries, written in Rust. An application opens an
in-memory graph or a durable local directory through a library call, and queries run in its own process. An optional
HTTP server exposes the SPARQL protocol. The architecture is in [DESIGN.md](../../DESIGN.md).

Every claim below links to the pull request that made the change, and every number links to the evidence file that
holds it. Evidence files record their own setup and limits; read them before quoting a number.

## What ships

**Libraries and command line.** Eight crates, `triplelight` and seven helpers (`triplelight-core`, `-iri`, `-rdf`,
`-sparql`, `-plan`, `-exec`, `-storage`), and a `triplelight` binary with `query`, `serve` (optional `server` feature),
`serve-store`, `build-disk` and `verify`. The Rust embedded API is in [docs/embedded/README.md](../embedded/README.md); an
async API for any executor is behind the `async` feature ([#101](https://github.com/odysa/triplelight/pull/101)).

**Language bindings** (each has a README in `bindings/`):

| Binding | Stores | Notes |
| --- | --- | --- |
| Python | in-memory and persistent | built from source with maturin; Python 3.9 or newer ([#123](https://github.com/odysa/triplelight/pull/123)) |
| Node.js | in-memory and persistent | prebuilt addons for macOS arm64, Linux x64 and Linux arm64 (glibc 2.31 or newer), Node 18 or newer ([#126](https://github.com/odysa/triplelight/pull/126)) |
| WebAssembly | in-memory only | CommonJS build for Node, ES module build for browsers and bundlers ([#126](https://github.com/odysa/triplelight/pull/126)) |
| C ABI, Go, Java 25 | in-memory and persistent | the Go and Java bindings wrap the C ABI; Arrow C stream output ([README](../../README.md)) |

**On-disk formats** ([docs/persistence.md](../persistence.md)). New stores are written as `RDFSNAP6` with four sorted
orders (SPO, PSO, POS, OSP), and SOP and OPS are served from them with the same rows in the same order
([#118](https://github.com/odysa/triplelight/pull/118), [#119](https://github.com/odysa/triplelight/pull/119),
[#124](https://github.com/odysa/triplelight/pull/124)). `--orders=6` keeps all six orders. `RDFSNAP4` has one dictionary
file in ID order that serves both lookups ([#83](https://github.com/odysa/triplelight/pull/83)); `RDFSNAP5` adds named
graphs ([#89](https://github.com/odysa/triplelight/pull/89), [#91](https://github.com/odysa/triplelight/pull/91)).
Older stores (`RDFSNAP2` to `RDFSNAP5`) stay readable.

**SPARQL.** SPARQL 1.1 query and update, with named graphs end to end: `GRAPH`, `FROM`, `FROM NAMED`, graph management,
and N-Quads and TriG loading ([#77](https://github.com/odysa/triplelight/pull/77), [#79](https://github.com/odysa/triplelight/pull/79),
[#78](https://github.com/odysa/triplelight/pull/78), [#82](https://github.com/odysa/triplelight/pull/82),
[#85](https://github.com/odysa/triplelight/pull/85), [#88](https://github.com/odysa/triplelight/pull/88)). Property paths, `DESCRIBE`
and the hash and time functions are supported. CI requires at least 323 tests of the W3C SPARQL 1.1 query suite to pass
([ci/w3c_floor.json](../../ci/w3c_floor.json)). A dot before a `GRAPH` block in quad data is accepted
([#102](https://github.com/odysa/triplelight/pull/102)).

**Parsers and terms.** The IRI resolver, the N-Triples, N-Quads, Turtle and TriG parsers and the RDF term types are
TripleLight's own; no Oxigraph crate is a runtime dependency, and the original crates remain only as test comparators
([#92](https://github.com/odysa/triplelight/pull/92), [#94](https://github.com/odysa/triplelight/pull/94),
[#96](https://github.com/odysa/triplelight/pull/96), [#103](https://github.com/odysa/triplelight/pull/103)). The code follows
the originals closely, so the licence notices travel with it ([#97](https://github.com/odysa/triplelight/pull/97),
[#104](https://github.com/odysa/triplelight/pull/104)).

## Measured results

Each line links to the evidence file. All measurements are descriptive and taken on one test machine; each file gives its setup and says how many sessions it covers.

- **Embedded analytics.** On BSBM BI at 10M triples through the Python API, summed query time over the 45 timed requests
  is 11.608 s and 13.145 s in two passes for TripleLight, against 130.025 s and 110.581 s for a hand-written DuckDB SQL
  baseline. DuckDB has no SPARQL; the baseline is described there
  ([docs/benchmarks.md](../benchmarks.md), the Python API table for BSBM BI, LUBM-100 and WatDiv aggregates).
- **One dictionary copy.** The BSBM-100M store shrinks from 12,533.1 MB to 7,936.3 MB (−36.7%); the six order files are
  byte-identical, and the dictionary conversion phase is about 30% shorter
  ([docs/unified-dictionary-100m-v1/README.md](../unified-dictionary-100m-v1/README.md), [#83](https://github.com/odysa/triplelight/pull/83)).
- **Four orders by default.** Stores are smaller: LUBM-1000 4.97 GB to 3.16 GB (−36%) and BSBM-100M 7.94 GB to 6.56 GB
  (−17%). Build time is not reliably faster; the evidence file says why
  ([docs/build-compare-orders-v1/README.md](../build-compare-orders-v1/README.md), [#124](https://github.com/odysa/triplelight/pull/124)).
- **Persisted planner statistics.** With a saved statistics file, statistics are ready 0.74 to 0.91 s after the start
  of open, against 20.5 to 25.8 s when they are rebuilt by a scan
  ([docs/startup36-persisted-stats/README.md](../startup36-persisted-stats/README.md)).
- **Where a disk build spends its time.** A four-order LUBM-1000 build took 654.8 s with a 2.31 GB peak resident
  set; the shard parse and sort took 38.7% and the order builds 26.4%
  ([docs/build-profile-v1/README.md](../build-profile-v1/README.md)). Another run of the same command took 435 s
  ([docs/parse-phase-v1/README.md](../parse-phase-v1/README.md)); run-to-run variation on the test machine was large.
- **Comparisons with other engines** (QLever, Virtuoso, Jena TDB2, RDF4J, Oxigraph) at 10M to 100M triples, with the
  answer checks and the cases where TripleLight is behind, are in [docs/report/evaluation.md](../report/evaluation.md).

## Compatibility and upgrade notes

- **Stores built by this release open in this release and later.** A store built with the new default (`RDFSNAP6`,
  four orders) cannot be opened by a binary from before [#119](https://github.com/odysa/triplelight/pull/119); there is no
  downgrade path. Use `--orders=6` to write the six-order layout that older binaries can read
  ([#124](https://github.com/odysa/triplelight/pull/124)).
- **Existing stores keep their layout.** Compaction keeps a base's order set, so a six-order store stays six-order
  ([#124](https://github.com/odysa/triplelight/pull/124)).
- **Turtle input always builds six orders;** `build-disk --orders=4` with Turtle input is an error
  ([#124](https://github.com/odysa/triplelight/pull/124)).
- **A term longer than 16 MiB** is refused at commit rather than accepted and then blocking compaction
  ([#95](https://github.com/odysa/triplelight/pull/95)).
- `triplelight verify` is faster and still exact ([#71](https://github.com/odysa/triplelight/pull/71)).

## Known limits

- **Platforms.** Persistent stores need Linux or macOS. The WebAssembly package is in-memory only. Rust 1.100 is
  required to build ([rust-toolchain.toml](../../rust-toolchain.toml)).
- **Disk builds** parse shards in parallel and overlap index builds; the LUBM-1000 profile kept an average of 2.9 of the host's 10 cores busy. They need scratch disk of about 1.7 to 2.1 times the input at the peak,
  mostly during parsing ([docs/build-compare-orders-v1/README.md](../build-compare-orders-v1/README.md),
  [docs/build-profile-v1/README.md](../build-profile-v1/README.md)). In the historical configurations QLever built the same data faster
  ([docs/report/evaluation.md, "Where TripleLight is behind"](../report/evaluation.md#where-triplelight-is-behind)); a dedicated-host load test is still pending.
- **Memory.** On LUBM-1000, block caches of 2 GB, 1 GB and 512 MB made the warm queries 3.6, 4.0 and 4.6 times slower than the
  default budget ([docs/cache-budget-sweep-v1/README.md](../cache-budget-sweep-v1/README.md)). Large answers are the main
  memory cost; JSON output is built in a bounded window ([#131](https://github.com/odysa/triplelight/pull/131)), but
  results are otherwise materialized before output.
- **SPARQL.** `LOAD`, `SERVICE` and `BNODE(string)` are not supported; N-Quads and TriG need IRI graph names; empty TriG
  blocks create no graph ([README](../../README.md)).
- **Numbers.** `xsd:decimal` arithmetic is exact within 96 bits and 28 fractional digits, and `xsd:integer` within 64
  bits; results outside that range are errors. This is stricter than XPath for decimal underflow ([DESIGN.md](../../DESIGN.md)).
- **One process per store directory,** enforced by a file lock.
- **Not yet 1.0.** Interfaces and on-disk formats may change in later releases.

## Next (in progress, not part of v0.1.0)

These are under way and make no claim about this release:

- **Evaluation on a dedicated machine.** A registered plan ([docs/eval-plan/PLAN.md](../eval-plan/PLAN.md)) for the cross-system comparison, with the
  gaps found in the pre-submission audit ([docs/paper-gaps-v1.md](../paper-gaps-v1.md)). The laptop numbers above are single-session and will be replaced.
- **RDF 1.2 and SPARQL 1.2.** Work has started on the W3C working drafts (triple terms, base-direction literals, the new functions, and result
  formats). v0.1.0 implements RDF 1.1 and SPARQL 1.1 only: it refuses triple terms and directional literals.
- **CSV and TSV results over HTTP.** Not in v0.1.0, which answers in SPARQL JSON.
