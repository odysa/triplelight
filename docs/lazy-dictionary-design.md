# Lazy, fallible disk dictionary: candidate design

Status: design only; no on-disk implementation or performance result yet. The existing RDFDIC01 dictionaries remain readable through the current eager path.

New dictionaries consist of immutable term-sorted and ID-sorted block files. Each record contains a full tagged `TermId` and an RDF term in its canonical N-Triples representation. Sorting and lookup must preserve exact RDF term identity, including language tags, lexical forms, blank-node labels and escaped characters. The ID index must not assume dense IDs: legacy snapshots can contain inline IDs, and separate ID namespaces use high bits. The term index must map each term to one ID; duplicate terms or IDs are corruption.

Blocks carry bounded entry counts, a byte length, and a SHA-256 checksum. The directory stores last key, absolute offset, length and checksum for each block. A checksum over the versioned header and complete directory binds bounds and keys; the snapshot manifest binds dictionary directory identities. Open validates magic, sizes, monotonic directory keys and checksums, without scanning all term payloads. Block reads use position-based I/O, exact-length checks, checksum verification, strict decoding and intra/inter-block order validation. The files are required to remain immutable while in use; cached data is not evidence of later file integrity. No mmap is required, so a later external truncation produces an I/O error on an uncached read rather than SIGBUS. A `verify` operation explicitly validates every block, term/ID bijection and consistency with the six triple indexes.

Both lookups first binary-search an in-memory block directory, then read and search one block through a byte-bounded cache. Eviction cannot invalidate a borrow: a lookup clones the block's `Arc` while holding its shard lock, releases that lock, and only then invokes `with_term` with a reference into the retained block. Errors must propagate from `lookup`, `resolve`, `with_term` and serialization to the HTTP 500/query-error path; `Ok(None)` only means absent. No callback may be invoked on failure. Cached blocks have the same invalidation limitation as index caches.

At build, create both sorted views with bounded scratch-backed sorting and fixed-fan-in merge. Write all blocks and directories, fsync files, then publish the snapshot manifest and fsync the generation and parent directories. Compaction uses the same creation path and retains old generations while readers exist. A crash or source/IO error must never publish a partial dictionary. Old snapshots should be migrated by writing a new generation, not by mutating open files. The existing 3x input-size strategy threshold is advisory, not a hard RSS bound.

Tests before integration: all RDF term kinds, duplicate/unknown IDs, differing/inline tags, empty dictionaries, block boundaries, malicious lengths, truncated files, wrong checksums, unsorted records, error propagation from cache misses and callback lifetime/reentrancy, old snapshots, and reopen after commit/compaction. Compare both views against an independent map, including randomized inputs. Then run LUBM/WatDiv result parity and measure fresh process open-to-first-query, sampled/peak RSS, cold-vs-warm limits, and compaction with old readers held. The targets (<1 s and <2 GiB respectively) are not established until measured. The metadata directory and cache budget also need measured overhead; sorting run-path lists and block directories grow with data and must not be described as a strict constant-memory guarantee.
